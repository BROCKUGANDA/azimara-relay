# 2. NON-NEGOTIABLE ENGINEERING RULES

These rules take precedence over speed and visual convenience.

## 2.1 No fake functionality

Do not use:
- Fake payment records in production.
- Hardcoded wallet balances.
- Fabricated transaction signatures.
- Simulated successful transfers.
- Fake settlement confirmations.
- Mock MultiHopper responses in production.
- Placeholder API integrations presented as complete.
- Fake AI recommendations presented as verified facts.
- Synthetic volume in business analytics.
- Buttons without working actions.

Mock fixtures may be used in unit tests and explicitly labelled development previews. They must never enter production execution paths.

When a dependency is not configured, expose a genuine setup or unavailable state.

## 2.2 No unauthorized financial execution

The system must never:
- Request seed phrases.
- Store private keys.
- Sign on behalf of customers without their explicit wallet authorization.
- Silently submit payments.
- Bypass approval policies.
- Change recipients after approval.
- Repeat an uncertain payment blindly.
- Treat API acceptance as proof of onchain completion.
- Treat an AI response as permission to transfer funds.

Every financially material action must be validated and authorized.

## 2.3 Do not invent APIs

Inspect the official MultiHopper OpenAPI specification, latest documentation, SDKs and current API response schemas before implementation.

Use actual documented endpoints and payloads.

The documentation currently describes:

- `POST /api/v1/transfers`
- `POST /api/v1/transfers/{transferId}/prepare`
- `POST /api/v1/transfers/{transferId}/confirm-broadcast`
- `GET /api/v1/transfers/{transferId}`
- The documented webhook registration and lifecycle interfaces.

Verify all current paths and requirements before writing the production adapter.

Do not assume the previous documentation response examples are a complete API schema.

## 2.4 Build for failure

Every external dependency may be unavailable.

Design for:
- RPC outages.
- Provider API outages.
- Wallet disconnections.
- Expired blockhashes.
- User rejection.
- Partial transaction broadcasts.
- Duplicate webhook delivery.
- Missing webhook delivery.
- Database transaction failures.
- Queue worker restarts.
- Browser refreshes.
- Network timeouts.
- Incomplete settlements.
- Rate limiting.
- Stale quotes.
- Provider status inconsistencies.

Never silently report success following an uncertain operation.

## Database rules

1. Use UUIDs for internal identifiers where appropriate.
2. Store financial amounts as exact integer base units or precise decimal representations.
3. Never use JavaScript floating-point numbers for authoritative token calculations.
4. Enforce unique organization-scoped external references.
5. Enforce wallet and transaction uniqueness where applicable.
6. Use database transactions for financially material state changes.
7. Index common organization, date, status and reference queries.
8. Apply tenant isolation at the query layer and, where appropriate, PostgreSQL Row Level Security.
9. Keep an immutable audit trail.
10. Use migrations and maintain rollback procedures.

Define relationships and delete behavior explicitly.

Do not use cascading deletion for financial records that must be preserved for audit purposes.

## 6.3 Wallet signing

Use supported wallet adapters.

Requirements:

1. Verify connected wallet.
2. Verify expected network.
3. Validate that the sending wallet matches `sourceOwner`.
4. Decode prepared transactions.
5. Validate transaction structure.
6. Verify transaction freshness.
7. Present authorization information.
8. Request wallet signing.
9. Broadcast in documented order.
10. Record signatures.
11. Wait for actual confirmation.
12. Submit provider confirmation calls.

Support both applicable legacy and versioned transactions as returned in the prepared bundle.

Do not modify transaction instructions to change provider-generated financial semantics.

The customer must see what they are signing through an intelligible transaction preview and the wallet's own authorization screen.

## 6.4 MultiHopper sequence

Implement exactly the documented prepare and confirm-broadcast lifecycle.

Important requirements:

- If `keeperFundingTx` exists, broadcast it first.
- Immediately make the intermediate confirmation call with the keeper funding signature and empty `routeInitSignatures`.
- Broadcast route initialization transactions.
- Broadcast orchestrator initialization where present.
- Broadcast session initialization transactions.
- Handle dispersion initialization for applicable multi-destination transfers.
- Wait for actual chain confirmation.
- Submit the final confirmation request.
- Verify resulting transfer status.
- Persist the transaction signatures and progress.

Implement resume logic.

The prepare endpoint exposes onchain progress and may omit transaction groups that have already been initialized. Use this information after interruptions rather than replaying already-confirmed transactions.

When an operation becomes uncertain, reconcile against the provider and Solana chain before deciding whether to continue, retry or escalate.

## 6.6 Fee handling

Always show fresh provider quotes.

Keep separate records for:

- Payment principal.
- Percentage fee.
- Per-hop charges.
- Network transaction costs.
- Screening fees where applicable.
- Estimated recipient proceeds.
- Confirmed provider fees.
- Actual settlement outcomes.

The currently published MultiHopper documentation describes a mainnet screening charge in the prepare workflow. Verify current fees using the provider's estimate and quote responses, never a fixed hardcoded amount.

      ↓

      ↓

      ↓

      ↓

      ↓

Requirements:

- Policy versioning.
- Amount thresholds.
- Recipient allowlists.

- Multiple approvers.
- Approver independence.
- Expiring approvals.
- Approval revocation.
- Policy-change history.
- Organization-specific rules.

An administrator must not silently alter a policy and then reuse an approval issued under the previous policy.

Implement clear separation of duties.
